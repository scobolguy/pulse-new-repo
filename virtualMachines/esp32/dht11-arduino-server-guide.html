Beginner project / about 30 minutes

Make a DHT11 tell the network how it feels.

Wire a temperature-and-humidity sensor to an ESP32, give it a tiny web server, then ask it for readings from a second node.

What you will build: one ESP32 reads the DHT11; another device asks for a JSON reading over your local Wi-Fi.

GET /api/climate

1Gather the parts

  • ESP32 development board
  • DHT11 temperature/humidity sensor
  • Jumper wires and USB cable
  • 4.7k-10k resistor for a bare sensor
  • USB cable for the ESP32
  • PlatformIO installed for this project

What changes in the firmware? The DHT11 driver and HTTP endpoint live in src/devices/dht11/. PlatformIO builds that folder into the existing ESP32 firmware; main.cpp registers the route when the feature flag is enabled. You do not upload a separate Arduino sketch.

The ESP32 environment already declares the Adafruit DHT library and its Unified Sensor dependency. Wi-Fi remains managed by the existing firmware; do not put Wi-Fi passwords into compiler flags.

2Connect the sensor

Turn the sensor so its front grille faces you. A bare, four-pin DHT11 is usually arranged like this. Some packaged modules have only three pins; follow the labels printed on the module.

Bare 4-pin DHT11

Front grille toward you +----------------+ | DHT11 | +----------------+ | | | | 1 2 3 4 VCC DATA NC GND
  1. DHT11 pin 1, VCC, to ESP32 3V3.
  2. DHT11 pin 2, DATA, to ESP32 GPIO 4.
  3. DHT11 pin 3, NC, leave it unconnected.
  4. DHT11 pin 4, GND, to ESP32 GND.

Add a 4.7k-10k resistor between VCC and DATA.

3-pin sensor module

Many modules already include the pull-up resistor. Use the printed pin labels; the physical order varies.

  1. VCC to ESP32 3V3.
  2. OUT or S to GPIO 4.
  3. GND to ESP32 GND.

Power note: use 3.3V with an ESP32. Do not let a 5V pull-up drive the ESP32 data pin. If using an Uno instead, check the exact sensor/module datasheet before powering it at 5V.

3Turn the ESP32 into a server

This is the server node: the existing firmware runs as usual, with the DHT11 feature enabled in the active PlatformIO environment. For this repo, that environment is esp32dev in platformio.ini.

These settings enable the feature, select GPIO 4, set the URL path, and explicitly include the device module in the firmware build:

[env:esp32dev]
; Keep the existing board, framework, library dependencies, and flags.
build_flags =
  ${env.build_flags}
  -std=gnu++17
  -DENABLE_PMACHINE
  -DPLATFORM_ESP
  -DENABLE_HTTPS
  -DENABLE_DHT11_HTTP_SERVER
  -DDHT11_DATA_PIN=4
  -DDHT11_HTTP_PATH=\\"/api/climate\\"

build_src_filter = +<*> +<devices/dht11/> ...

Do not replace the environment's existing build_flags or build_src_filter. Add the three DHT flags and the +<devices/dht11/> inclusion to the existing entries. The DHT library is already listed under this environment's lib_deps.

The implementation is intentionally small:

src/devices/dht11/
  Dht11HttpServer.h
  Dht11HttpServer.cpp

DHT11_DATA_PIN and DHT11_HTTP_PATH are compile-time settings from PlatformIO. The module reads the sensor and returns JSON. The firmware's existing Wi-Fi setup provides network access; its HTTP server registers the module's route during startup.

  1. Wire DHT11 DATA to GPIO 4, then connect the ESP32 to USB.
  2. Build the existing firmware with platformio run -e esp32dev.
  3. Upload it with platformio run -e esp32dev -t upload.
  4. Find the ESP32 IP from its normal startup/status output or your router's device list.
  5. From a device on the same network, request http://<ESP32-IP>/api/climate.

A successful response looks like this:

{"valid":true,"temperatureC":23.0,"humidityPercent":48.0}

The sensor node is now serving readings. The JSON names are temperatureC and humidityPercent.

If the sensor cannot be read, the route returns HTTP 503 and {"valid":false,"error":"sensor_read_failed"}.

4Ask from another ESP32 node

The client does not need the DHT11 driver. It only needs to call the server's HTTP endpoint. Replace the IP with the address of the sensor ESP32:

curl http://192.168.1.50/api/climate

A JavaScript node can make the same request and use the returned values:

const response = await fetch("http://192.168.1.50/api/climate");
if (!response.ok) throw new Error(`Sensor server returned ${response.status}`);

const reading = await response.json();
console.log(reading.temperatureC, reading.humidityPercent);

A second ESP32 node can make the same GET with its HTTP client. Both boards must be on a network that allows devices to contact one another. The client can poll every few seconds; avoid requesting DHT11 readings faster than once every two seconds.

5If it does not work

The server returns a sensor error

Check VCC, GND, and DATA wiring. Confirm the data wire goes to GPIO 4 and the code says DHT11, not DHT22. Add the pull-up resistor if you have a bare four-pin sensor.

The browser or client cannot reach the server

Use the current server IP, put both nodes on the same network, and keep the full path /api/climate in the URL. The address is local to your network; this route does not expose the sensor to the public internet.

Readings fail when requested quickly

DHT11 is a slow sensor. Wait at least two seconds between readings. The client example waits five seconds.

What is compiled

The DHT11 HTTP module is part of the project's ESP32 firmware build, alongside PMachine. It adds an HTTP sensor endpoint; it does not add a new PMachine opcode or change PMachine programs. Enable it only in the PlatformIO environments that have the DHT11 physically connected.
