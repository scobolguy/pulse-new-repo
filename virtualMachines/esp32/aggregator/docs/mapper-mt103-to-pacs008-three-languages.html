MT103 → PACS.008 with a Mapper

How to build the same CBDS payment-conversion service in Pascalish, VBish, and Cobolish. All three compile to the same pcode and produce byte-identical output on the PMachine.

The three programs

Each service declares its librarian role, defines (or imports) the CBDS mapper, and binds the input queue → mapper → output queue. Conversion rules compile to native opcodes — nothing is string-interpreted at runtime.

Pascalish canonical

The reference language. The mapper is declared inline and a router applies it.

service "cbds-converter" on local;
role code_librarian;
library "payments-common" from librarian;
use "payments-common" as CORE;

mapper "cbds-mt103-to-pacs008" source "swift-mt103" target "pacs" begin
  map "block4.20" to "Document.FIToFICstmrCdtTrf.GrpHdr.MsgId" using "output = trim(src)";
  map "block4.32A.date" to "...CdtTrfTxInf.IntrBkSttlmDt" using "output = yymmddtoiso(src)";
  map "block4.32A.amount" to "...IntrBkSttlmAmt.#text" using "output = mtamounttodecimal(src)";
  // ... 16 more MAP rules ...
end;

router "cbds-mt103-to-pacs008-route" input "swift.mt103.parsed" begin
  output "cbds.pacs.outbound"
    when "output := 1;"
    transform "output := map('cbds-converter.cbds-mt103-to-pacs008', src);";
end;

begin
end.

VBish declarative

The shortest form. Import Mapper pulls the shared CBDS definition from the Mapping Librarian; one Route line wires the flow.

Service "vbish-mt103-to-pacs008" On Local

Role Code_Librarian
Library "payments-common" From Librarian
Use "payments-common" As Core
Import Mapper "cbds-mt103-to-pacs008" From Mapper

Route "swift.mt103.parsed" To "cbds.pacs.outbound" Using Mapper "cbds-mt103-to-pacs008"

Cobolish MAPPING SECTION

COBOL-85 divisions plus a MAPPING SECTION in the DATA DIVISION. Paths are bare; rules use BEGIN output = fn(src) END.

IDENTIFICATION DIVISION.
PROGRAM-ID. CBDS-CONVERTER.
PULSE SERVICE "cbds-converter" ON LOCAL.

ROUTE "swift.mt103.parsed" TO "cbds.pacs.outbound" USING MAPPER cbds-mt103-to-pacs008.

DATA DIVISION.

MAPPER-ENTRY cbds-mt103-to-pacs008
    SOURCE-TYPE swift-mt103
    TARGET-TYPE pacs.

MAP-RULE block4.20 TO Document.FIToFICstmrCdtTrf.GrpHdr.MsgId
    USING BEGIN output = trim(src) END.

    GOBACK.
END PROGRAM CBDS-CONVERTER.

How a mapper works

A mapper is a named set of field-level rules. Each rule reads one value out of the source message by path, transforms it, and writes it to a target path. The rules are the only place conversion logic lives — the service code just points a queue at the mapper.

1. Declare the mapper

Give it an id and the source/target type ids (e.g. swift-mt103 → pacs).

2. Add MAP rules

Each rule maps a source path to a target path with a conversion like trim(src) or mtamounttodecimal(src).

3. Route through it

Bind an input queue to an output queue using the mapper. The runtime applies every rule per message.

4. It compiles to pcode

Rules become native opcodes (["SRC","YYMMDD_TO_ISO"]) and the route becomes ROUTE_MAP_RUN.

The compile pipeline

VBish / Cobolish → portable Pascalish → pcode + program map → PMachine Pascalish ↗

VBish and Cobolish compile into Pascalish (the canonical portable form), then the shared Pascalish compiler emits pcode and the program map. Pascalish compiles directly. All three produce the same artifacts.

Compiled, not interpreted

Conversion rules are stored as native opcode lists in the program map, executed directly by the PMachine. There is no runtime string parsing of rules on either the JavaScript or the ESP32 PMachine.

Rule written asCompiles to opcodesWhat it does
output = trim(src)["SRC","TRIM"]Trim whitespace
output = upper(trim(src))["SRC","TRIM","UPPER"]Trim then uppercase
output = yymmddtoiso(src)["SRC","YYMMDD_TO_ISO"]260702 → 2026-07-02
output = mtamounttodecimal(src)["SRC","MT_AMOUNT_TO_DECIMAL"]12500,45 → 12500.45
output = mtpartyname(src)["SRC","MT_PARTY_NAME"]Strip account line, keep name
output = mtchargebearertoiso(src)["SRC","MT_CHARGE_TO_ISO"]SHA / OUR → ISO charge code

The router line compiles to a single dispatch opcode:

// route: "swift.mt103.parsed" -> mapper -> "cbds.pacs.outbound"
ROUTE_MATCH_QUEUE "swift.mt103.parsed"
JZ ROUTER_SKIP_3
ROUTE_EVAL_WHEN "output := 1;"
JZ OUT_SKIP_4
ROUTE_MAP_RUN "cbds-converter.cbds-mt103-to-pacs008"   // the mapper, compiled
ROUTE_EMIT "cbds.pacs.outbound"
OUT_SKIP_4:
ROUTER_SKIP_3:
Smaller interpreter. Because rules are pcode, the PMachine does no trim(src)-style string matching per message. The same opcode executor runs on the JS PMachine and the ESP32 firmware, which share one opcode manifest (OP_ROUTE_MAP_RUN = 0x63).

Verified result

All three programs were run against the same MT103. Output is byte-identical (timestamp excluded) across Pascalish, VBish, and Cobolish.
